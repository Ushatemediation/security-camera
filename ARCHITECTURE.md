# Архитектура security_camera

Документ снят с реального кода (`main.py`, `notifier.py`, `audio.py`). Фиксирует
потоковую модель, память и известные проблемы/ограничения.

## Потоки

| Поток | Роль | Обмен |
|-------|------|-------|
| `CaptureThread` | читает камеру на полной скорости | последний кадр под `lock`, `frame_seq`, `new_frame` Event |
| `RecognitionWorker` | InsightFace: детект+эмбеддинг+сравнение | один слот `_pending` (последний кадр), результат под `_result_lock` |
| `PersonTracker` | YOLOv8n + ByteTrack | один слот `_pending`, `_tracks` под `_result_lock` |
| `WriterThread` | пишет кадры в mp4 | `queue.Queue(maxsize=queue_size)`, `_lock` вокруг writer |
| `DiskCleaner` | чистит старые записи | файловая система |
| `AudioRecorder` | пишет микрофон в катящиеся WAV-сегменты | `_segments` под `_lock` |
| `TelegramNotifier._thread` | отправка фото/видео + ffmpeg-мукс; фазы PROCESSING/SENDING через `SendJob` | `queue.Queue` заданий |
| `Pipeline` (main.py) | стейт-машина пайплайна: IDLE→RECORDING→PROCESSING→SENDING_TELEGRAM; склейка и отправка — её методы | `finalized_q` (Writer→Pipeline), события `SendJob` (notifier→Pipeline) |

Связь потоков — через «последний кадр» и очереди, без общих мутабельных структур
кроме защищённых `lock`. Это предотвращает гонки, но означает, что при перегрузке
промежуточные кадры теряются осознанно (дропаются), а не копятся.

## Память — узкие места и что сделано

1. **Pre-buffer** (`RingBuffer`). Раньше `list` + `pop(0)` — O(n) на кадр и без
   гарантии по памяти. Теперь `deque(maxlen=pre_seconds*fps)` — O(1) и жёсткий
   предел. При 1080p 5с@30fps это ~150 кадров ≈ 0.9 ГБ — основной потребитель;
   если мало RAM, уменьшайте `recording.pre_seconds` или `motion.process_fps`.
2. **Копии кадров на каждом шаге**: `get_frame()` копирует кадр, `submit()` копирует
   ещё раз в воркер. Один кадр живёт одновременно в 2–3 копиях (main, recognition,
   tracker). Осознанный компромисс ради отсутствия гонок.
3. **`_pending` в воркерах** держит только последний кадр (старые заменяются) —
   очередь не растёт.

## CPU

- Motion gate: MOG2 + `cv2.resize` только на `process_fps`; тяжёлые модели — только
  при движении/трекере/записи. Раньше был «safety check», гонявший InsightFace
  каждые 2 с впустую — убрано.
- `allowed_modules=["detection","recognition"]` и `CPUExecutionProvider` — только
  нужные модули InsightFace, без GPU-провайдеров.

## Стейт-машина пайплайна (`main.py`)

| Состояние | Что происходит | Выход из состояния |
|-----------|----------------|--------------------|
| `IDLE` | детекция (motion → лицо/трекер) | цель в кадре → `RECORDING` |
| `RECORDING` | кадры пишет `WriterThread` | цель ушла / лимит `recording.max_seconds` → `PROCESSING` |
| `PROCESSING` | writer финализирует mp4; notifier склеивает аудио (ffmpeg) по окну записи | `SendJob.processing_done` → `SENDING_TELEGRAM` |
| `SENDING_TELEGRAM` | отправка снимка + mp4 со звуком в Telegram | `SendJob.sending_done` → `IDLE` |

Переходы делает только `Pipeline` (внутри основного цикла): писатель кладёт готовый
файл в `finalized_q`, воркер нотификатора выставляет события `SendJob`, а «добро» на
отправку (`go_send`) выдаётся при входе в `SENDING_TELEGRAM`. Новая цель в кадре
переводит пайплайн в `RECORDING` из любого состояния, не дожидаясь окончания
отправки предыдущего клипа (стейт отражает стадию последней записи).

## LED камеры Logitech (`led_control.py`)

UVC class-specific `SET_CUR` на Extension Unit 11 (selector 9, GUID `ffe52d21-…`,
payload `[03 00 01 MODE 01]`): включение при старте, выключение при выходе
(`led.shutdown()`). Камера ищется среди устройств Logitech (приоритет — C922
0x085c). Если нет `pyusb`/`libusb`/USB-доступа (типовой случай — Windows без
WinUSB-драйвера) — фича тихо пропускается и на запись не влияет.
Отладка: `python led_control.py --list | --probe | --set 1`.

## Известные ограничения (осознанные)

- Синхрон A/V. Видео пишется CFR по слотам: пропуски кадров (детекция грузит
  главный цикл) закрываются дублями последнего кадра (`WriterThread.padded`),
  длительность клипа = `слоты / fps` и совпадает с окном аудио — дорожки больше
  не «разъезжаются». Метки аудиоблоков — по началу блока; остаточный сдвиг
  устройства ввода правится `audio.sync_offset_ms` (+ = звук позже), а
  `aresample=async=1` не даёт накопиться дрейфу к концу клипа. Диагностика —
  строка «Запись завершена: … дубли N, дропы M»: много дублей = цикл не успевает
  кормить писателя, ставьте `recording.fps` по камере и уменьшайте нагрузку.
- Запись (`VideoWriter`, mp4v) пишет **без** звуковой дорожки; звук добавляется
  при отправке (ffmpeg-мукс). `mp4v` → при отправке перекодируется в H.264/AAC.
- `HOME_CAMERA` под системным аккаунтом: аудио-устройство может быть недоступно —
  тогда видео уходит без звука (не критично).
- Recorder/tracker воркеры при некорректном завершении вызывают `os._exit(1)`
  (падение процесса ловится супервизором и Task Scheduler).
- `WriterThread.start_recording` ждёт финализации предыдущей записи не дольше 10 с
  (`_finalize_done`); при экстремально медленном диске теоретически возможна гонка
  finish/start — унаследованное ограничение, на практике очередь дренится за мс.
- При завершении программы стейт-машина ждёт финализацию последней записи,
  упаковывает остаток `finalized_q` в `SendJob` и разрешает отправку до вызова
  `notifier.shutdown()` — последний клип не теряется (см. `finally` в `main.py`).
